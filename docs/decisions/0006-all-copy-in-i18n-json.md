# 0006 · 표시 문구는 100% i18n JSON에 둔다

## 결정

화면에 보이는 모든 문구는 `src/lib/i18n/{ko,en}.json`에 있다.
`src/helpers/datas/**`에는 id·날짜·URL·이미지 경로·기술명처럼 언어와 무관한 값만 둔다.

## 맥락

데이터 파일이나 컴포넌트에 한국어를 넣는 순간 영어 페이지가 반쪽이 된다.
그리고 이 저장소는 데이터 한 곳이 **네 출력**(화면·JSON-LD·`/llms.txt`·챗 시스템 프롬프트)으로
퍼지므로, 어느 하나에 문구를 하드코딩하면 네 출력이 서로 어긋나고 구조화 데이터와 본문의
불일치가 SEO에 역효과를 낸다.

가장 위험한 성질: **`t()`는 키를 못 찾으면 키 문자열을 그대로 반환한다.**
예외가 나지 않으므로 오타는 lint·typecheck·build를 전부 통과해 배포 HTML에 박힌다.
실제로 `profile.rolee` 같은 키가 배포본에 노출될 수 있음을 실측으로 확인했다.

## 포기한 대안

- **i18n 라이브러리(next-intl 등)** — 정적 프리렌더 + 두 route group 구조에서 얻는 것이 적고
  의존성만 는다. 필요한 것은 점 표기 경로 조회 하나였다.
- **키 미발견 시 throw** — 화면이 통째로 죽는다. 지금은 타입 계층이 오타를 먼저 잡으므로 불필요하다.

## 강제하는 가드

| 대상 | 가드 |
|---|---|
| 정적 키 오타 | **타입** — `TranslationKey`가 ko.json에서 파생된 유니온. TS가 `Did you mean '"profile.role"'?`까지 알려준다 |
| `t`/`tList` 혼용 | **타입** — `TranslationListKey` 분리 |
| ko/en 파리티(키 + **배열 길이**) | `scripts/i18n-guard.mjs` R6 |
| 데이터 id ↔ i18n 키 | `scripts/i18n-guard.mjs` R7 |
| 데이터 계층이 UI를 import | `scripts/arch-guard.mjs` R1 |
| 렌더 결과의 키 누수 | `verify:runtime` V3(본문 + JSON-LD 각각) |

**타입이 못 하는 일**: `` `${slug}.items.${itemId}` `` 같은 2단 교차곱 동적 키.
TS가 실존하지 않는 조합까지 전개해 버린다. 그 자리는 `DynamicKey`로 명시적으로 이스케이프하고
(코드에서 눈에 보이도록 일부러 greppable하게 뒀다) R7이 실제 데이터 id를 실제 JSON과 대조해 대신 지킨다.

## 재검토 트리거

언어가 셋 이상이 되면 파리티 검사가 쌍이 아니라 N-way가 되어야 한다.
그때 i18n-guard의 비교 로직을 일반화하거나 라이브러리 도입을 다시 검토한다.
