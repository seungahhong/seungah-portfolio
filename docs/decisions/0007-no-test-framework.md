# 0007 · 테스트 프레임워크를 도입하지 않는다

## 결정

vitest·jest·testing-library를 도입하지 않는다. 대신 빌드 산출물을 실제로 서빙해 관측하는
하네스(`pnpm verify`)와 스냅샷 대조(`pnpm verify:snapshot`)를 오라클로 쓴다.

## 맥락 — 결정적인 이유

**이 저장소가 실제로 겪은 사고 2건은 단위 테스트가 원리적으로 잡을 수 없는 종류였다.**

1. 상단 프로바이더의 `useSearchParams`로 정적 페이지 HTML이 통째로 빈 사고
2. 서버 렌더에서 로케일이 무시된 사고

둘 다 컴포넌트를 jsdom에서 렌더하면 정상 동작한다. 결함은 **프로덕션 빌드가 만든 HTML에서만**
드러난다. 아키텍처 위반 probe 5종 중 4종도 마찬가지였다.
**이 저장소의 결함 분포는 단위 테스트가 아니라 산출물 대조를 요구한다.**

부차적으로: devDependency 4~6개와 설정 파일, 지속적인 버전 추적 표면이 늘어난다.
가드레일 전체를 신규 의존성 0으로 만든 이 저장소의 방향과 어긋난다.
(Next 16 + React 19 RSC + Turbopack 조합에서 jsdom 기반 서버 컴포넌트 테스트의 성숙도는
실제로 시도해 보기 전엔 단정할 수 없다 — 여기서 막히면 비용이 몇 배가 된다.)

## 포기한 것 (정직하게)

- **좁은 단위의 회귀 위치 특정.** 산출물이 틀렸을 때 "어느 함수가 틀렸는지"를 하네스는 알려주지 않는다.
- **클라이언트 상호작용 검증.** 탭 키보드 이동(roving tabindex)·테마/언어 토글·`popstate` 구독은
  curl로 관측되지 않는다. 현재 이 영역은 **검증되지 않은 채로 있다**.

## 강제하는 가드

`pnpm verify` = lint → typecheck → build(prebuild 가드 포함) → 산출물 서빙 후 84개 단정.
`pnpm verify:snapshot`은 리팩터의 등가성 센서다 — 타입만 바꾸는 변경은 산출물이 그대로여야 하고,
"키를 잘못 바꿔 *다른 유효한 문자열*이 렌더되는" 실패 모드는 타입이 못 잡지만 본문 diff는 잡는다.

## 재검토 트리거

- **(a)** `lib/**`에 데이터 변환 분기가 늘어 "산출물이 틀렸다"에서 원인 모듈을 특정하기 어려워질 때
  → 그때 vitest를 **`lib/**`의 순수 함수에만** 좁게 도입한다. 컴포넌트 테스트는 여전히 도입하지 않는다.
- **(b)** 클라이언트 상호작용의 회귀가 **실제로 발생**했을 때
  → 그때 정답은 vitest가 아니라 **Playwright 1개**다. 브라우저가 있어야만 드러나는 결함이기 때문이다.
